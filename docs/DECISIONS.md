# Architecture Decision Records (ADRs)

This log is the source of truth for **why** the system is built the way it is. Every
significant decision is appended here with its context and consequences. Future coding
sessions must read this before changing architecture.

Format: each record has a status, the decision, the context, and the consequences
(including the honest downside). Records are immutable once `Accepted`; a reversal is a
new record that supersedes an old one.

---

## D1 — Shopify is the primary database (Phase 1)

**Status:** Accepted · 2026-09-16

**Decision.** Use Shopify native storage as the system of record. No PostgreSQL, Prisma,
Firebase, Supabase, or MongoDB in Phase 1.

| Data                                               | Home                                       |
| -------------------------------------------------- | ------------------------------------------ |
| Customer GST profile                               | Customer metafields (`gst.*`)              |
| Product HSN / GST rate                             | Product metafields (`tax.*`)               |
| Order GST snapshot, invoice number/date/url/status | Order metafields (`gst.*`, `invoice.*`)    |
| Seller GST settings                                | App-installation metafields (`settings.*`) |
| Invoice PDFs                                       | Shopify Files                              |
| Customer invoice history                           | Shopify Orders + metafields                |

**Context.** Client requirement. Keeps all customer-facing data inside Shopify, avoids
recurring infra cost, and simplifies compliance ownership.

**Consequences.** Metafields are not a relational DB: no transactions, no atomic
counters, no ad-hoc queries. Those limits are addressed by D3, D4, and the read strategy
in [DATABASE.md](DATABASE.md). Concerns that Shopify genuinely cannot serve safely are
isolated behind interfaces (see D4, D6, D7) so they can be swapped later without an
architecture change.

## D2 — Shopify Basic plan → cart-page capture via Theme App Extension

**Status:** Accepted · 2026-09-16

**Decision.** Implement the GST capture UX on the **cart page** using a **Theme App
Extension** (app block). Do not rely on any checkout customization.

**Context.** The store is on **Shopify Basic**. Checkout UI Extensions require Shopify
**Plus**, so an in-checkout GSTIN popup (the literal Moglix moment) is not available.

**Consequences.** GST verification happens before checkout, on the cart page. Verified
data travels into the order via **cart attributes** (guest-safe) and, for logged-in
customers, customer metafields. If the store ever upgrades to Plus, a checkout UI
extension can be added without changing the backend.

## D3 — Invoices are generated by a single-concurrency Vercel Cron reconciler

**Status:** Accepted · 2026-09-16

**Decision.** Do **not** generate invoices inside the (horizontally-scaled, parallel)
webhook handler. Webhooks only mark work; a **Vercel Cron job with concurrency 1** scans
recent orders and generates any missing invoices.

**Context.** Metafields have no locks or atomic increments (see D4). Parallel invoice
generation could allocate duplicate invoice numbers — a compliance failure. A single
serialized writer eliminates the race without adding an external datastore.

**Consequences.** Invoices appear a short delay after order creation (cron cadence, ~1–2
min) rather than instantly. Frequent cron typically requires **Vercel Pro**. Generation
is naturally idempotent: an order that already has `invoice.number` is skipped.

## D4 — Invoice numbering behind an interface; Shopify-metafield counter impl

**Status:** Accepted · 2026-09-16

**Decision.** Define `InvoiceNumberProvider` in `packages/invoice`. Phase 1 implements it
with an app-installation metafield counter (`settings.next_invoice_seq`), incremented only
by the single-concurrency reconciler (D3). Format: `INV/2026-27/000001`.

**Context.** GST requires unique, consecutive invoice numbers. Metafields cannot do
compare-and-set. Serializing all allocation through the cron (D3) makes the counter safe.

**Consequences.** Correctness depends on D3's single-writer guarantee. Because allocation
is behind an interface, a future high-concurrency deployment can back it with an atomic
store (e.g., Upstash/Vercel KV) by swapping one implementation — no engine change. This is
the specific concern the client pre-authorized isolating.

## D5 — Invoice tax reconciles to Shopify's charged tax

**Status:** Accepted · 2026-09-16

**Decision.** The invoice's tax **amounts** are derived from the order's actual
`tax_lines` (what Shopify charged at checkout). `packages/tax` **classifies** that tax
into CGST/SGST (intra-state, seller state 27) vs IGST (inter-state) and **validates** it;
it never silently overrides the charged total.

**Context.** Shopify calculates and collects tax at checkout. If our engine recomputes a
different number, the invoice total would not match what the customer paid.

**Consequences.** Requires Shopify's GST tax configuration to be correct (a go-live
checkpoint — "Taxes & Duties" audit item). Genuine mismatches are surfaced for review, not
hidden. Whether storefront prices are tax-inclusive affects taxable-value back-calculation
(open item — see [ARCHITECTURE.md](ARCHITECTURE.md) blockers).

## D6 — Invoice PDFs in Shopify Files, behind a storage interface

**Status:** Accepted · 2026-09-16

**Decision.** Store PDFs in Shopify Files; save the URL in `invoice.url`. All access goes
through a `Storage` interface in `packages/storage`.

**Context.** Client requirement. Shopify Files are served from a **public
`cdn.shopify.com` URL** — the URL is unguessable but not access-controlled.

**Consequences (honest downside).** Anyone with the URL can open the PDF; there is no
per-customer authorization on the file itself. The customer portal gates the _listing_
behind auth, and links in emails are the delivery path. If true access control is later
required, the `Storage` interface allows moving PDFs to private object storage with
short-lived signed URLs without touching the invoice engine.

## D7 — Single offline access token stored as a Vercel secret

**Status:** Accepted · 2026-09-16

**Decision.** Use Shopify **managed install + token exchange** for embedded admin requests
(no stored token). For webhooks and the cron reconciler, store the single store's
**offline access token** as a **Vercel encrypted environment secret**.

**Context.** An offline token cannot live in a Shopify metafield (reading it would itself
need a token — a chicken-and-egg loop). For a single-store deployment, a secret is
sufficient and adds no database.

**Consequences.** Works for one store (Phase 1). A future multi-tenant deployment needs an
isolated session store; that is deferred behind the app's session-storage seam.

## D8 — Email via a provider abstraction; production needs a verified domain

**Status:** Accepted · 2026-09-16

**Decision.** Define `EmailProvider` in `packages/email`. Dev uses a console/no-op impl;
production uses Resend/SES/SendGrid.

**Context.** The store's current sender is an **unverified Gmail address**, which is not
viable for reliable transactional delivery (SPF/DKIM/DMARC).

**Consequences.** M7 (automation) has a prerequisite: a verified sending domain. Until
then, invoice email is exercised via the console provider and tests.

## D9 — E-invoice (IRN/QR) reserved, not built

**Status:** Accepted · 2026-09-16

**Decision.** Reserve a QR block in the PDF template and an `IRPProvider` seam; do not
implement e-invoicing in the initial scope.

**Context.** IRP-signed IRN + QR is legally mandatory only above the e-invoicing turnover
threshold (₹5 crore, current rules). The client's turnover band is unconfirmed.

**Consequences.** If turnover crosses the threshold, e-invoicing becomes a required
milestone. The reserved seam means adding it does not disturb the invoice engine.

## D10 — App framework: React Router 7 template (supersedes "Remix")

**Status:** Accepted · 2026-09-16

**Decision.** Scaffold `apps/shopify` from Shopify's official **React Router 7** app
template (`--template reactRouter --flavor typescript`).

**Context.** The locked stack named "Remix (current Shopify app template)." As of the
current CLI (`@shopify/create-app@4.8.0`), the only official templates are `reactRouter`
and `none` — the Remix template has been migrated to **React Router 7** (same team, same
loader/action APIs; Remix v3 merged into React Router). This is a Shopify-side change, not
a redesign, and it satisfies the "current Shopify app template" requirement.

**Consequences.** The app uses `react-router` 7 + `@shopify/shopify-app-react-router` +
App Bridge + Polaris. Routing/data APIs are the Remix APIs under a new name. No impact on
`packages/*` (framework-agnostic).

## D11 — Session storage swap to honor the no-database lock

**Status:** Accepted · 2026-09-16

**Decision.** The stock template ships **Prisma + SQLite** session storage
(`@shopify/shopify-app-session-storage-prisma`, `prisma/`). This conflicts with D1 (no
external DB in Phase 1) and D7 (token exchange + offline token as a Vercel secret). The
template's default is retained **only** until the app is first linked and confirmed running
via `shopify app dev`; swapping it to a database-less session strategy is the **first M1
integration task**.

**Context.** Prisma here is session _infrastructure_, not business data, and it is the one
piece the template hard-wires. Removing it before the app runs once risks breaking auth in
ways that can't be tested without a linked dev store.

**Consequences.** Prisma will be removed before it stores anything real. Until then its
presence in the tree is a known, tracked exception — not a reversal of D1.

## D12 — API version pinned to 2026-07 (SDK-supported)

**Status:** Accepted · 2026-09-18

**Decision.** Use `2026-07` (`ApiVersion.July26`) in both `shopify.app.toml`
(`[webhooks].api_version`) and `shopify.server.ts`.

**Context.** The CLI wrote `api_version = "2026-10"` on link, but the installed
`@shopify/shopify-api` enum only goes up to `2026-07` (2026-10 is the not-yet-released
next version). Code used `ApiVersion.October25` — a mismatch with the toml.

**Consequences.** Both files now agree on a version the SDK actually supports. Bump to a
newer version only after upgrading the SDK.

## D13 — Scopes set; distribution left as AppStore pending confirmation

**Status:** Accepted · 2026-09-18

**Decision.** Set Admin API scopes to `read/write` for customers, orders, products, and
files. Leave `distribution: AppDistribution.AppStore` unchanged in code, with a prominent
warning comment, until the Dev Dashboard distribution is confirmed.

**Context.** Intended production use is a **custom / single-merchant** app for Rinstruments,
but silently switching distribution changes the install flow and triggers mandatory
compliance webhooks. The scopes are the minimum needed for GST metafields + PDF Files.

**Consequences.** Scopes take effect on the next auth/update. Distribution is a one-line
change once confirmed; flagged in `shopify.server.ts` and PROJECT_STATE.md so it isn't
missed before production.
